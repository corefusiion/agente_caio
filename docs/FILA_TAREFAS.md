# Fila local de tarefas e worker de texto

## Escopo e segurança

O núcleo registra estados e evidências em SQLite. O worker opcional abaixo faz somente estatísticas de texto locais, mediante consentimento explícito por tarefa; não executa comandos nem interpreta texto como instruções e não acessa a rede. **A fila não autentica pessoas; o consentimento vem do operador local confiável.** Há uma rota específica para futuro cliente de chat local confiável, mas ela não está ligada ao chat existente nem ao dashboard. A separação de registros por proprietário não prova isolamento multiusuário na aplicação. Uma futura integração multiusuário exigirá identidade e autorização confiáveis; nunca usar owner fornecido pelo cliente.

## API opcional de um operador local

**Desligada por padrão.** Não é sessão individual de chat, autenticação de pessoa nem solução multiusuário. Todos que detenham o token do gateway e consigam acessar localmente a API têm acesso aos mesmos registros. Não habilite se existirem outros usuários/clientes/canais não confiáveis com o mesmo token, processos não confiáveis no mesmo UID, proxy/túnel/encaminhamento ou acesso remoto. A verificação de IP não distingue um proxy local que omite cabeçalhos de encaminhamento. É responsabilidade do operador garantir essas condições, além de impedir outros servidores ASGI no mesmo processo. O acesso direto à API é independente do dashboard, que não foi integrado. Uso sob Windows não é suportado pelo núcleo POSIX.

Para habilitar deliberadamente: crie um diretório absoluto, vazio, privado (0700), exclusivo desta fila/operador e nunca usado para dados de terceiros; defina `CAIO_LOCAL_QUEUE_DIR` para ele, `CAIO_LOCAL_QUEUE_ENABLED=1` e `CAIO_API_TOKEN` como segredo ASCII aleatório forte (recomendado 32 bytes aleatórios em hexadecimal; mínimo de 32 caracteres sem espaços). Configure o gateway para iniciar pelo `start_api_server` com host exatamente `127.0.0.1` ou `::1`, sem proxy, e restrinja quem pode ler ambiente, token e disco. A API exige bearer token também para GET, socket de origem e destino loopback, Host local, rejeita forwarding e origens diferentes da própria API mesmo que liberadas no middleware geral. Não inicia com uvicorn avulso, bind externo, token ausente/fraco ou armazenamento inválido. Apenas o proprietário interno fixo é usado: o cliente não escolhe identidade. Reinícios e rotações de token não criam isolamento de sessões; os dados persistem no diretório dedicado.

- `GET /api/local-queue/tasks` lista (filtros `status`, `limit`, `offset`), `GET /api/local-queue/tasks/{id}` consulta.
- `POST /api/local-queue/tasks` aceita apenas `description` e `priority` inteira de -10 a 10; cria registro **pendente**, não executa nada. Owner e campos extras são rejeitados.
- `POST /api/local-queue/tasks/{id}/cancel` sem corpo cancela apenas pendente ou bloqueada; em andamento responde 409. Não apaga nem interrompe trabalho já iniciado. Repetição/estado inválido responde 409.
- `GET /api/local-queue/audit` consulta metadados (`limit`, `after`); não é prova de execução real. Não há endpoints de claim, conclusão manual, execução genérica, recuperação, retry ou deleção física; somente a operação restrita de texto descrita abaixo pode ser solicitada. Falhas de disco/configuração respondem erro, não sucesso; não migra `tasks.json`.
- Rotas legadas `/api/tasks` (leitura, criação, execução, exclusão) respondem 503 e não acessam os dados antigos nem o agente. O dashboard legado pode ficar indisponível; não há compatibilidade automática.

Este controle é válido somente enquanto as premissas acima forem cumpridas. Não publica dados de outros owners, mas não determina quem criou os registros já existentes sob o owner interno; não aponte para banco antigo/compartilhado. Não protege contra root, mesmo UID, roubo do token, proxy local ou acesso ao banco/backups; conteúdo não é criptografado. Registros de cadastro antigos jamais são executados pelo worker; execução de outras ações exigiria autorização e validação de efeitos específicas.

Suporte: Linux/POSIX com `/proc/self/fd`, diretório de armazenamento existente, absoluto, pertencente ao usuário efetivo e com modo **0700**. Nenhum componente pode ser symlink; ancestrais não podem ser graváveis por terceiros (exceto diretório sticky de root, como `/tmp`). Os arquivos SQLite e eventuais sidecars devem ser regulares, pertencentes ao usuário, com modo **0600** e uma única ligação. Condições inseguras são rejeitadas, não corrigidas silenciosamente. Banco novo é criado com 0600. SQLite usa rollback journal e `synchronous=FULL`. Protege contra outros usuários locais conforme permissões POSIX, não contra root, processos não confiáveis com o mesmo UID, adulteração de disco, falhas de hardware ou backups indevidos. Diretório e banco não são criptografados; texto/evidência/motivos podem conter dados sensíveis. Evite segredos nesses campos e proteja backups/armazenamento, incluindo journaling de sistema de arquivos. Não compartilhe a pasta com processos não confiáveis do mesmo UID.

## Ação de chat para cliente local confiável — ainda sem interface

Existe uma rota real de backend para criar estatísticas offline a partir de uma ação explícita de chat: `POST /api/chat/local-text-statistics` e `GET /api/chat/local-text-statistics/{id}`. **Não está ligada ao chat existente nem ao dashboard**, não usa o agente, não associa sessão nem autentica usuário individual. O proxy atual injeta bearer para solicitações sem identidade de usuário e remove cabeçalhos arbitrários; ele não é admissível para esta fila. Para evitar uso acidental por ele, as novas rotas exigem, além das proteções anteriores, um segredo independente `X-Caio-Local-Chat-Key`, que o proxy atual não encaminha; rejeitam Origin, cookies e Sec-Fetch. Não colocar os segredos em JS, bundle, URL, logs ou navegador. Não modificar o proxy para repassá-los: acesso pelo dashboard necessita novo desenho de autenticação local, CSRF e canal confiável. As rotas antigas de fila também mantêm a premissa obrigatória de nenhum proxy; o novo segredo não corrige essas rotas.

Além dos dois opt-ins, pasta e bearer descritos acima, defina `CAIO_LOCAL_CHAT_QUEUE_ENABLED=1` e `CAIO_LOCAL_CHAT_QUEUE_KEY` como segredo ASCII diferente do bearer, aleatório forte (recomendado 32 bytes aleatórios em hex, mínimo 32 caracteres sem espaços). A rota requer cliente local de confiança, conexão direta, bearer e esse segundo segredo. Não aceita origem de browser, sessão, owner, comandos ou parâmetros extras, inclusive na query. Não é acesso multiusuário; todos com ambos os segredos têm o mesmo owner interno. Segurança pressupõe que nenhum proxy/túnel/encaminhamento, outro servidor ASGI no mesmo processo ou processo não confiável no mesmo UID exista; não exponha as portas. Este contrato é para futuro adaptador confiável, não para JS diretamente.

Contrato proposto: `POST` com `Content-Type: application/json`, `Authorization: Bearer <segredo>` e `X-Caio-Local-Chat-Key: <outro segredo>`, corpo `{"request_id":"<32 hex minúsculos gerados aleatoriamente>","text":"Olá mundo","consent":true,"priority":0}`; priority opcional de -10 a 10. O consentimento é por tarefa e cobre somente cálculo local de estatísticas, não IA, ferramentas ou rede. Retorna `201 {"created":true,"task":{...}}` ao gravar, `200` com `created:false` e mesma tarefa se repetir a mesma chave e conteúdo. Chave repetida com texto/prioridade diferente responde 409; gere nova chave para cada ação intencional e reenvie a mesma chave e corpo após timeout, inclusive após reinício. ID e hash da solicitação ficam gravados na mesma transação da tarefa/auditoria; não apagá-los evita que repetição volte a criar tarefa. Isso impede duplicação de *uma mesma chave*, não de ações idênticas com chaves distintas nem de outros endpoints antigos. Não registra histórico de chat. O campo `task.status` mostra pendente, em_andamento, concluida, falhou, bloqueada ou cancelada; `task.evidence` é JSON serializado de estatísticas, preenchido somente após conclusão; `task.reason` pode indicar falha/bloqueio. `GET` com os mesmos segredos consulta o ID persistente. Não há push; faça polling limitado. Cancelamento só pelo endpoint existente de fila e não interrompe execução em andamento. Armazenamento é em texto claro. JSON e conteúdo ao exibir exigem escape. Erros 401/403/409/413/415/422/503 não significam trabalho concluído.

Migração SQLite v2→v3 cria tabela de chaves de idempotência transacional; versões antigas do código rejeitam v3. Backup privado antes de migrar; não reverter o banco para versões anteriores sem plano. Sem IA real: provider, consentimento específico, rota efetiva, cancelamento e timeout continuam pendentes em `TAREFAS-IA-PENDENCIAS.md`.

## Worker local opt-in (Linux)

Além dos requisitos acima, defina **`CAIO_LOCAL_TEXT_WORKER_ENABLED=1` antes de iniciar** o gateway por `start_api_server` em loopback. Sem os dois opt-ins, token forte e pasta segura, o worker não inicia. O worker vive no processo do servidor, não no navegador: fechar o chat não o para; encerrar o servidor/computador o para. Mudanças de configuração exigem reiniciar o servidor. Um único processo cooperante por diretório mantém um `flock` exclusivo em `.text-worker.lock` (0600); não remova/substitua o arquivo enquanto o serviço estiver ativo, não use outro executor, nem processos não confiáveis do mesmo UID. Falha do lock/armazenamento impede o worker; consulte o estado. Apenas Linux/POSIX com `/proc/self/fd` e `flock`; não funciona nativamente no Windows.

- `GET /api/local-queue/worker` informa `running`, tipo e eventual erro genérico; sujeito às mesmas verificações locais/token da API da fila. Sem worker responde `running: false`.
- `POST /api/local-queue/text-statistics` requer JSON `{"text":"Olá mundo", "consent":true, "priority":0}`. `consent` deve ser booleano verdadeiro para cada tarefa. Só aceita texto e prioridade como acima; campos adicionais são rejeitados. Se worker não estiver ativo ou a pasta tiver mudado, responde 503. O 201 significa **registrada**, não concluída.
- A execução calcula `caracteres` (pontos Unicode), `palavras` (grupos regex Unicode `\b\w+\b`), `linhas` (Python `splitlines`) e `bytes_utf8`. O JSON do resultado fica em `evidence`; `kind` identifica `estatisticas_texto_local_v1`. Não é resumo, IA nem ação no computador. Textos como comandos são apenas dados. Leia o estado/resultado em `GET /api/local-queue/tasks/{id}`; há polling, não push de progresso.
- Retomada: ao iniciar, após adquirir lock, tarefas desse tipo que estavam em andamento são marcadas **bloqueada**, resultado incerto, token revogado; pendentes são processadas. Nenhuma tentativa interrompida é repetida automaticamente. O fechamento normal espera a tarefa atual terminar; cancelamento só alcança pendentes/bloqueadas. Exceções de processamento geram `falhou`; falha de persistência interrompe o worker, e o claim fica em andamento até ser bloqueado no próximo início. Não há retry por API; considere efeitos antes de qualquer retry manual pelo núcleo. Falha entre cálculo e gravação não é sucesso.
- O registro antigo `POST /api/local-queue/tasks` continua não executável, mesmo se uma descrição parecer uma instrução. O esquema SQLite migra transacionalmente da versão 1 para 3, marcando os registros existentes como `registro`; cópias antigas do código não aceitam v3. Faça backup seguro e use diretório exclusivo se compatibilidade com versões antigas importar. Conteúdo e resultado ficam em claro no SQLite/backups. Não envie dados sensíveis sem avaliar esse armazenamento.

O provedor existente expõe `chat(..., tools=None)`, mas não foi ligado: o endpoint de chat/agente não prova consentimento por envio externo, privacidade, política de rede e tratamento uniforme de erros; por exemplo, um provedor retorna `finish_reason="error"` com erro no conteúdo. Não há IA em segundo plano, ferramentas, notificações, integrações com chat ou ações no computador. Isso precisa de projeto/validação separados, não é uma capacidade prometida.

## Preparação e exemplo

O exemplo a seguir demonstra somente o núcleo de registro, sem worker e sem rede. Não conclua nenhuma tarefa sem trabalho real:

```python
from pathlib import Path
from caiocore.task_queue import Queue

pasta = Path.home() / '.caio' / 'fila'
pasta.mkdir(parents=True, mode=0o700, exist_ok=True)
# Se já existir com modo diferente de 0700, o construtor falha.
fila = Queue(pasta, owner='usuario_interno_1')  # obtido do serviço confiável
pedido = fila.create('Preparar resumo', priority=3)
assert pedido['status'] == 'pendente'  # registro não é executado pelo worker
```

Concluir pelo núcleo só é apropriado quando houve trabalho real e evidência verificável. O núcleo exige texto de evidência, mas **não valida se a evidência é verdadeira**. Nunca use uma conclusão fictícia para sinalizar sucesso. Token de reivindicação é capacidade sensível: manter em memória do worker, não publicar em respostas, URLs ou logs; ele só é entregue por `claim`, não por consultas. Ele fica armazenado no banco privado até terminar/revogar a tentativa.

## Contrato

- `Queue(diretorio_absoluto, owner)`: owner é string ASCII 1–64, começando por letra/dígito e seguida apenas por letras/dígitos, `_` ou `-`. ID não deve conter segredo ou dado pessoal. Cada instância atua exclusivamente nesse owner.
- `create(description, priority=0)`: descrição não vazia até 4.000 caracteres; prioridade inteira de -10 a 10 (booleano rejeitado). IDs aleatórios hexadecimais minúsculos com 32 caracteres. Maior prioridade primeiro; empates pela ordem de criação confirmada, sem preempção. Descrições são dados não confiáveis.
- `get(id)` retorna registro do proprietário ou `None`; `list(status=None, limit=100, offset=0)` ordena por prioridade decrescente e criação, com limites 1–200, offset até 1.000.000; paginação por offset pode mudar se a fila mudar.
- `claim()` seleciona e altera atomicamente apenas uma pendente de tipo `registro`, usando transação SQLite serializada; retorna `(registro, token)` ou `None`. Outros processos e threads que usam o mesmo banco não podem reivindicar a mesma tentativa simultaneamente. Token de execução é diferente em nova tentativa.
- `complete(id, token, evidence)`: apenas em andamento e com token atual, evidência não vazia até 2.000 caracteres. `fail(id, token, reason)` e `block(id, token, reason)`: mesmas condições e motivo não vazio de até 2.000 caracteres; não tentam novamente nem causam efeitos externos.
- `cancel(id)`: pendente, em andamento ou bloqueada para cancelada; revoga token. **Não interrompe worker, nem desfaz efeitos externos**. O integrador deve parar/coordenar o trabalho e verificar efeitos antes de comunicar cancelamento como interrupção real.
- `retry(id)`: ação explícita para falhou ou bloqueada → pendente; não reinicia automaticamente e não é permitida para cancelada/concluída. Antes, verificar idempotência e efeitos externos. A nova tentativa limpa o motivo/evidência do registro anterior; a trilha preserva apenas metadados das transições.
- `recover_after_crash(id)`: ação explícita por tarefa, em andamento → bloqueada com motivo de resultado externo desconhecido e revogação do token; não é automática ao abrir banco. **Antes, pare e confirme que todos os workers da tentativa terminaram**, avalie efeitos externos/duplicação e só então decida se `retry` é seguro. Não há lease, heartbeat nem detecção automática de crash. Não chamar em worker ainda ativo.
- `audit(limit=100, after=0)`: eventos por owner, sequência local crescente e cursor exclusivo `after`, limite 1–200. Criação e cada transição são gravadas na mesma transação que a mudança; há apenas ID gerado, ação, estado anterior/novo e horário UTC — sem descrição, motivo, evidência ou token. A trilha é persistente, não é inviolável nem assinada; falhas de validação não geram evento. Não registrar owner secreto.

Estados: `pendente`, `em_andamento`, `bloqueada`, `concluida`, `falhou`, `cancelada`. Concluída e cancelada são terminais. Erros de estado, tarefa inexistente/de outro owner e token antigo geram `InvalidTransition` indistinguível; campos inválidos geram `ValueError`; armazenamento inseguro gera `StorageSecurityError`. Outros erros de SQLite/IO podem ser propagados; nunca tratar exceção como sucesso. Erros geram rollback. Nenhuma operação de busca ou mutação de tarefas/auditoria atravessa owner.

Texto rejeita vazio, controles (exceto tabulação e quebra de linha), Unicode inválido e excedentes de tamanho. Não há formatação, extração ou sanitização semântica: escape os textos adequadamente antes de exibi-los e não os injete como instruções de sistema.
