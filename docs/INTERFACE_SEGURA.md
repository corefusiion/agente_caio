# Interface local do Caio: desenho, uso e limites

## O que foi alterado

A UI usa URLs relativas `/api` (inclusive downloads e SSE) e o endpoint legado `GET /events`. `dashboard/secure_proxy.py` serve o build e encaminha apenas `/api` e o `GET /events` exato para a API, acrescentando o Bearer **no servidor**, sem enviá-lo ao navegador. Host e Origin precisam corresponder a `localhost:<porta>` ou `127.0.0.1:<porta>`; escritas sem Origin são bloqueadas. O proxy rejeita origens cruzadas, metadados Fetch cross-site/same-site, duplicatas de cabeçalhos críticos, transferência chunked, caminhos de travessia e corpos acima de 10 MiB. Não encaminha cookies, Authorization do navegador, headers de proxy ou segredo Evolution. Não habilita CORS. A rota de webhook não é publicada no proxy da interface. O gateway mantém sua própria autenticação e validação de Host/Origin.

A imagem do dashboard agora usa Python sem root, não Nginx; portanto o antigo `nginx.conf` não participa desta configuração. O servidor Vite não é mais proxy de API: `npm run dev` isolado não é modo de operação com o agente. Isso evita que uma rota de desenvolvimento injete credenciais sem validar a origem. Para testar a UI conectada, gere `dist` e use o proxy abaixo.

## Premissas de segurança

Isto é uma interface **para a própria máquina**, sem login de usuário. Qualquer processo local e qualquer contêiner com acesso à rede privada compartilhada são considerados confiáveis; não é isolamento entre usuários da mesma máquina. Não exponha a porta 8080 ou a rede interna na LAN/Internet, nem coloque este proxy atrás de outro proxy público: alguém que o alcance pode falsificar Host/Origin e usar a credencial injetada. Para acesso remoto é necessária outra arquitetura com autenticação individual, TLS e proteção CSRF; não basta adicionar portas ou hosts. No Compose as portas publicadas estão vinculadas a 127.0.0.1; use Docker Engine atualizado (28 ou posterior) e firewall, já que versões antigas têm ressalvas de exposição de portas publicadas em loopback. Proteja acesso ao Docker, ao ambiente de processo e ao arquivo de configuração; variáveis do Compose são visíveis a quem pode inspecionar os contêineres. Não use o token em `VITE_*`, código, URL, histórico compartilhado ou bundle.

## Preparação

- É preciso ter as dependências Python do projeto, Node/npm e dependências do dashboard instaladas e uma configuração real revisada; este ambiente de desenvolvimento não tinha npm, dependências frontend, Docker nem acesso de instalação.
- Gere um token diferente de qualquer outro segredo, com 32 bytes criptográficos aleatórios, codificado em 64 caracteres hexadecimais minúsculos. O proxy se recusa a iniciar com token ausente ou fora desse formato. Configure o **mesmo** valor no gateway e proxy. Exemplo em um shell privado: `export CAIO_API_TOKEN="$(python -c 'import secrets; print(secrets.token_hex(32))')"`. Não cole o valor em conversas. Ao reiniciar os processos use o mesmo token; rotacione-o reiniciando ambos.
- A API usa o arquivo `config.json` no diretório atual, se existir; senão usa `~/.caiocore/config.json`. Não copie uma configuração real sobre outra. Revise credenciais, allowlists e integrações antes de iniciar `gateway`, que pode iniciar canais e tarefas. A porta efetiva é `gateway.port` no JSON, independentemente da opção visual `--port` do comando.

## Local, sem Compose

1. Em `dashboard`, execute `npm ci` e `npm run build` onde as dependências possam ser obtidas com segurança; o artefato é `dashboard/dist`. `npm ci` pode precisar de rede e não foi executado aqui.
2. Na configuração efetivamente carregada pelo gateway, defina `gateway.host` como `127.0.0.1` e `gateway.port` como `18790`. Mantenha a chave do provedor e canais somente se revisados. Assim a API não escuta fora da máquina.
3. Exporte `CAIO_API_TOKEN` como acima e inicie `caio gateway` a partir de um ambiente com o projeto instalado. No mesmo ambiente herdado, inicie `python dashboard/secure_proxy.py`. Acesse `http://127.0.0.1:8080` nessa máquina. Ambos precisam permanecer ativos. O proxy não executa nem inicializa o agente.
4. Em outros shells o mesmo token precisa ser transferido por meio privado; não gere outro token independente. Pode definir `CAIO_PROXY_PORT` para outra porta local, usando a mesma porta no navegador. Não altere `CAIO_PROXY_BIND` para uma interface externa.

## Compose local

1. Tenha Docker Compose e imagens/dependências necessárias. Prepare um arquivo JSON real e válido, externo ao repositório, acessível para leitura pelo UID 10001 do contêiner. Defina nele `gateway.host` como `0.0.0.0` e `gateway.port` como `18790`, para ser alcançável pelo proxy na rede privada. **Não exponha outras portas.** Uma configuração incorreta ou canal sem credenciais pode impedir a inicialização do agente.
2. Exporte `CAIO_API_TOKEN` no shell e `CAIO_CONFIG_FILE` com caminho absoluto para esse arquivo. `docker compose --profile agent up --build` inicia ambos os serviços; acessar `http://127.0.0.1:8080` na mesma máquina. O perfil exige ativação explícita e pode iniciar integrações configuradas. Não usar Swarm nem Traefik público. `depends_on` não garante prontidão: espere o gateway iniciar; erros 502 podem ocorrer antes disso.
3. A configuração montada continua somente leitura, preservando a proteção anterior. Alterações de configurações feitas pela interface podem falhar ao persistir; planeje uma forma segura de edição fora do contêiner. O workspace é o volume `caio_workspace` existente. O token existe em ambiente dos dois contêineres, não na imagem ou build.
4. Limitações não corrigidas: os endpoints Google em `caiocore/server/api.py` tentam criar `caio-stack/core` no diretório atual, que na imagem é `/app`, pertencente ao root. O processo UID 10001 não consegue criá-lo na imagem padrão: configuração de credenciais/token Google falha. Da mesma forma, o motor de documentos usa `cwd/out` e não consegue criar `/app/out` nessa imagem. Esses caminhos também não fazem parte do volume persistente. Além disso, os agendamentos são gravados em `/home/caio/.caiocore/cron/jobs.json`, fora do volume de workspace; serão perdidos ao recriar o contêiner. É preciso corrigir o backend/Compose para usar diretórios privados, graváveis e persistentes, e testar; não exponha credenciais para contornar o problema.

## WhatsApp / Evolution

A credencial `CAIO_EVOLUTION_WEBHOOK_TOKEN` é **independente** do token da API; sem ela a API rejeita o webhook. Para uso, configure no ambiente do gateway um segredo forte e exclusivo e faça o emissor ou um gateway confiável enviar `X-Evolution-Webhook-Token`. A configuração precisa ser compatível com a versão real do Evolution; não foi verificado se a instalação permite esse cabeçalho. O endpoint direto é `POST /api/webhooks/evolution` na porta da API e continua protegido pelo middleware; o proxy da interface devolve 404 para webhooks. A API no Compose só publica 18790 em loopback: um Evolution externo não chegará por essa porta; não a exponha publicamente como atalho. Para Evolution remoto, é necessária uma entrada separada autenticada, com TLS, limite de tamanho/frequência, validação de origem e rede, e revisão de Host; essa infraestrutura não foi implementada nem testada. Confira também `docs/WHATSAPP_SECURITY.md` e a allowlist. A integração não foi desabilitada nem afirmada como funcional.

## Evidência e pendências

- Na validação adicional com credenciais falsas e sockets locais reservados previamente, foram corrigidos dois defeitos do proxy: redirecionamentos 301/302/303/307/308 perdiam o cabeçalho Location, e pedidos Range para download eram ignorados. Agora o Location só é encaminhado para a mesma origem (outro destino ou Location ausente/duplicado resulta em 502); Range/If-Range e Content-Range/Accept-Ranges são encaminhados. Testes reproduziram antes a falta do Location e o retorno 200 inteiro em vez de 206; depois passaram, inclusive com redirecionamento externo bloqueado, If-Range e Range inválido. Os processos de teste usam ambiente isolado e arquivos temporários, sem herdar credenciais nem tocar serviço existente na porta 18790.
- Executado `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -p pytest_asyncio.plugin -q tests/test_interface_secure_proxy.py tests/test_runtime_guardrails.py tests/test_security_api_boundary.py tests/test_document_download_security_response.py`: 22 passaram, com quatro avisos. O fluxo testado percorre o proxy e a API FastAPI reais em localhost, com agente determinístico simulado (sem modelo real): mensagem e sessão, filtragem de cabeçalhos, bloqueios e evento SSE ao vivo. O arquivo baixado é uma fixture temporária, não um documento real gerado pelo agente. Essa evidência não valida a renderização, build React ou operação do gateway completo.

- Executado `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q tests/test_interface_secure_proxy.py tests/test_security_api_boundary.py`: 12 passaram. Incluem `GET /events`, duplicatas e enquadramento HTTP, caminhos codificados e esgotamento/liberação dos slots de conexão. O proxy e a API ASGI reais rodaram por sockets locais; a UI foi substituída por um HTML estático de teste. Verificados API Bearer, POST same-origin até 503 esperado (agente ausente), negativa para origens/hosts errados, POST sem Origin, preflight malicioso, webhook, caminhos, token fraco e SSE com keepalive de 15 segundos. Os testes existentes verificam também encaminhamento do webhook autorizado com canal simulado.
- O autoload de plugins pytest falha devido a incompatibilidade preexistente entre logfire e opentelemetry; foi desativado apenas no comando de teste. Não instalamos nem baixamos dependências.
- Sem npm, frontend instalado ou Docker, **não foram testados** build React, imagem/Compose, renderização em navegador, gateway completo, mensagens reais, provedores, Evolution real, download de documento real ou Git. Testar esses pontos em ambiente com dependências antes de considerar a interface pronta. O parse YAML básico não substitui `docker compose config` nem `up`.
- O proxy é uma implementação local pequena, não um servidor de produção endurecido contra DoS. Limita a 64 conexões simultâneas e aplica timeout de 30 segundos às operações no socket do cliente, mas um cliente lento pode manter slots ocupados; quando todos estão em uso, novas conexões são fechadas. SSE usa conexões persistentes e ocupa slots. Não suporta WebSocket nem exposição remota. O conteúdo e comportamento dos agentes/canais não foram modificados nesta tarefa.
