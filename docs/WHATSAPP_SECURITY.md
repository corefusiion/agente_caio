# Segurança dos canais WhatsApp

- Evolution: configure `channels.evolution.allowFrom` com números completos com DDI, apenas dígitos, ou o JID direto `<número>@s.whatsapp.net`. Lista vazia ou sem entradas válidas nega todas as mensagens recebidas e enviadas. O endereço precisa ser um JID direto numérico; grupos, status, LIDs e identificadores ambíguos são bloqueados. Mensagens maiores que 4096 caracteres também são bloqueadas.
- Bridge: configure `channels.whatsapp.allowFrom` da mesma forma e defina `channels.whatsapp.bridgeToken` com um segredo aleatório forte, único e privado (por exemplo, gerado com `python -c "import secrets; print(secrets.token_urlsafe(32))"`). Não inclua o valor em arquivos compartilhados, logs ou código. Proteja o arquivo de configuração e restrinja os usuários locais. Se a bridge for iniciada separadamente, passe o mesmo valor em `BRIDGE_TOKEN` no ambiente privado do processo Node. O comando de login já passa `bridgeToken` para `BRIDGE_TOKEN`. Os dois lados exigem o token; `bridge_url` deve apontar para `ws://localhost` ou `ws://127.0.0.1`. A bridge aceita conexões em 127.0.0.1, não em uma interface pública.
- A autenticação da bridge exige a resposta `auth_ok`; versões antigas sem essa confirmação deixam de se conectar. A allowlist da bridge nega entradas/saídas por padrão e recusa grupos e `@lid` mesmo que o número alternativo esteja disponível: isso pode impedir algumas conversas modernas. Não use correspondência de LID sem uma associação confiável e validada. Um cliente que possua o token tem acesso direto à bridge; proteja o token como uma credencial de acesso completo.
- **Atenção à cópia antiga:** o comando de login reutiliza `~/.caiocore/bridge/dist/index.js` existente sem reconstruir. Essa cópia pode manter a implementação antiga e insegura mesmo após atualizar o repositório. Desative-a e substitua-a/recompile-a usando o código corrigido antes de iniciar a bridge; preserve quaisquer dados próprios existentes. Alterar apenas o repositório não atualiza uma bridge já copiada ou em execução.
- A allowlist não autentica o remetente HTTP do webhook Evolution. É necessário autenticar a rota do webhook com segredo verificado antes do processamento, limitar tamanho/frequência e proteger exposição e transporte. Apenas conferir `instance` ou o número enviado no JSON não prova a origem. A API Evolution e o webhook exigem configuração/testes correspondentes antes de exposição pública.
